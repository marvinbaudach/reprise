# Track-Kontextmenü-Vereinheitlichung — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ein einziger, kontextabhängiger Track-Row-Kontextmenü-Builder für alle fünf Ansichten (Library-Tracks, Album-Detail, Artist-Detail, Playlist, Queue), gebaut aus einer reinen Funktion, ohne globale Einträge, ohne „Play"-Eintrag, mit kontexteigenen destruktiven Aktionen und Missing-/Multi-Zustandslogik — verankert als neue `CTX-`-Regeln im Regelwerk.

**Architecture:** Der Kontextmenü-Code liegt bereits als *ein* geteilter Builder vor ([track_list_context_menu.rs:147](../../../crates/reprise-gnome/src/ui/track_list/track_list_context_menu.rs#L147) verzweigt über `ViewSource`). Wir extrahieren die Menü-Entscheidungen in ein neues, **display-freies** Modul `track_menu.rs` mit zwei reinen Funktionen — `build_track_menu(inputs) -> gio::Menu` (Modellstruktur) und `action_states(context, selection) -> ActionStates` (Ausgrau-Logik) — plus reine Eingabetypen (`MenuContext`, `SelectionSummary`, `PlaylistEntry`).     pub go_to_artist: bool,
    pub show_in_files: bool,
    pub trash: bool,
    pub edit_tags: bool,
}

**Semantik (verbindlich):**
- `summarize_selection`: leere Slice → alles `false`, `count 0`, `all_missing false`. `same_album`/`same_artist`/`same_folder` sind für 1 Track trivially `true`. - `action_states`:
  - `enqueue = s.count > 0 && !s.any_missing`
  - `go_to_album = s.count > 0 && s.same_album`
  - `go_to_artist = s.count > 0 && s.same_artist`
  - `show_in_files = s.count > 0 && !s.any_missing && s.same_folder`
  - `trash = s.count > 0 && !s.any_missing`
  - `edit_tags = s.count > 0 && !s.all_missing`

**Section-Aufbau je Kontext** (Trennung durch `append_section`):

- **LibraryTracks:** [Play next · Add to queue] ⟂ [Add to playlist ▸ · Edit tags…] ⟂ [Go to album · Go to artist] ⟂ [Show in Files (+ Show in Missing files falls `any_missing && !is_missing_view`)] ⟂ [Remove from library… · Move to Trash…]

## Task 5: Queue — `Move to top`

**Files:**
- Modify: `crates/reprise-gnome/src/ui/playback/queue_transport.rs`

**Interfaces — Consumes:** `queue_row_mapping::QueueRow` (bestehend). **Produces:**
```rust
impl PlayerController {
    /// „Move to top" (Queue-Menü): verschiebt die selektierten Composite-Rows
    /// an den ANFANG der Play-Next-Lane (spielt als Nächstes), in
    /// Selektionsreihenfolge. Up-Next-Snapshot-Rows werden dabei in die
    /// Play-Next-Lane promoted (aus dem Snapshot entfernt). Now-Playing wird
    /// übersprungen. Rückgabe: Anzahl bewegter Rows.
    pub(in crate::ui) fn move_queue_rows_to_top(&self, rows: &[QueueRow]) -> usize;
}
```

**Algorithmus** (reine Kernfunktion `fn move_rows_to_front(context: &mut Queue, pending: &mut UpNextQueue, rows: &[QueueRow]) -> usize`, testbar mit nackten `Queue`/`UpNextQueue` wie `successor_after_purge`):
1. `base = context.current_order_position()`.
2. In `rows`-Reihenfolge die zu bewegenden ids sammeln: `PlayNext(i)` → `pending.ids()[i]` (falls in range); `UpNext(off)` → `context.id_at_order_position(base+1+off)` (nur falls `base` `Some`); `NowPlaying` → überspringen. Parallel `play_next_indices` und `snapshot_positions` merken.
3. Entfernen (Batch, stabil, vor dem Prepend berechnet): `pending.remove_positions(&play_next_indices)`; `context.remove_order_positions(&snapshot_positions)`.
4. `pending.prepend(&collected_ids)` (Front, Reihenfolge erhalten).
5. Rückgabe `collected_ids.len()`.
`move_queue_rows_to_top` ruft `move_rows_to_front` unter kurzen, disziplinierten Borrows auf und `notify_queue_changed()` genau dann, wenn `> 0` bewegt wurde.
