## What the app can honestly show today — measured, not assumed

`TrackRow` over UniFFI carries exactly `uri, title, artist, album,
duration_ms`. The core's own `Track` **does** carry `rating` and `play_count`
(`models.rs`), they simply never cross the boundary.

So the play-count badge and the star rating in the frames are **real data one
field away**, not decoration. They are in scope, and the FFI grows by two
fields to carry them.

**What has no backend at all, and must therefore not appear:**

- **Desktop sync.** The frames show `aurora.local`, "Wi-Fi gekoppelt · vor
  2 Min", pending play counts, mirrored playlists, MTP fallback, a sync history.
  **None of it exists on Android.** No pairing, no transport, no queue of
  pending changes.
- **Lyrics.** The core has a lyrics module; the FFI exposes nothing.
- **Playlists and queue as destinations.** The FFI has no playlist call.

**These are not to be mocked.** A screen that shows "Wi-Fi gekoppelt" while
nothing is paired is exactly the fabrication this codebase refuses elsewhere —
the same rule that made `MissingReason::Unknown` unable to delete anything and
`identity: None` better than an invented identity. Ship the frames whose data
exists; record the rest as designed-but-unbuilt.

### M3a — Artwork crosses the boundary

M3's centrepiece is a 364 dp cover, and artwork does not cross the FFI at all —
every cover slot in M2 is the honest no-artwork symbol. Measured before
splitting this out:

- The cover pipeline is **already source-aware**: `read_cover_tag_with_source`,
  `resolve_source_with_source` and `thumbnail_with_source` all take
  `&dyn LibrarySource`, so embedded pictures and sidecar images are reachable
  over SAF without a new reader.
- **`cover::cache_dir()` is hard-wired to `dirs::cache_dir()`** — XDG, plus the
  same global assumption in `cover_download`. On Android that is the wrong
  place, and it is exactly the pattern this codebase has paid for repeatedly:
  the core assuming something about the platform instead of being told.
- The desktop resolves covers **lazily, per row, off the main thread**
  (`ui/cover/cover_loader.rs` — resolve + thumbnail in a worker, with a recycle
  token), never inside the list query. Android must do the same.
- `ThumbnailSize` is a fixed pixel ladder (32/48/96/192/256/1024) sized for
  desktop density. A 56 dp row and a 364 dp cover on a 3× phone are not on it.

- [x] **The cache root becomes something the platform provides**, not something
      the core assumes. The desktop keeps XDG and does not change; Android
      passes its app-private cache directory — `Library::open` already receives
      `app_private_directory`. No hidden global, no mutable static.
- [x] **One lazy call per track** across the FFI, returning a cached thumbnail
      path or nothing. **Never inside `list_tracks`** — the paging contract from
      `#253` and the M2 window behaviour stay untouched, and decoding 200 covers
      inside a query would break both.
- [x] Kotlin resolves off the main thread, per visible row, and survives
      recycling — a scrolled-away row must not overwrite a newer one.
- [x] **No network.** Downloading covers is a separate question with its own
      policy; embedded art and sidecar images are what exists locally today.
- [x] Decide what size the phone actually asks for, and say why. Do not force
      the desktop's ladder onto a density it was not measured for.
- [x] The M2 status-bar defect above.

### M3b — Now Playing

#### Measured 2026-08-04, so nobody re-derives it

- **Seek is nearly there.** `PlaybackBackend::seek_to(position_ms: i64)` is in
  the core contract (`playback.rs:222`), `AndroidPlaybackPort::seek_to` already
  crosses the boundary (`playback.rs:58`), and `Media3PlaybackPort` already
  implements it (`Media3PlaybackPort.kt:108` → `player.seekTo`). The only thing
  missing is an exported method on `AndroidPlaybackSession` — the object Kotlin
  actually drives, which today offers exactly `play_tracks`, `toggle_pause`,
  `next`, `previous`, `snapshot` (`playback_session.rs:243`).
- **Shuffle and repeat are complete in the core and invisible at the boundary.**
  `Queue::set_shuffle` (`queue.rs:236`), `Queue::set_repeat` (`queue.rs:307`),
  and — this is what makes a *state* button possible — the readbacks
  `is_shuffled()` (`queue.rs:302`) and `repeat()` (`queue.rs:312`), over
  `Repeat { Off, All, One }` (`queue.rs:12`). Nothing is exported, and
  `AndroidPlaybackSnapshot` (`playback_session.rs:14`) carries only `state`,
  `current_index`, `position_ms`, `duration_ms`, `error`. The UI could not
  render the current mode today even if it could set it.
- **The rating setter is id-addressed.** `stats::set_rating(conn, track_id: i64,
  rating: i32)` clamps to 0–5 and is **silent on a missing track** — zero rows
  updated is not an error. `TrackRow` (`browse.rs:8`) carries no id, and no
  public URI→id lookup exists in the core; three call sites inline
  `SELECT id FROM tracks WHERE path = ?1` by hand.
- **Android never counts a play.** `stats::record_play(conn, track_id,
  now_unix)` and the half-played predicate `stats::should_count_play(
  max_position_ms, duration_ms)` exist, and outside a test fixture the Android
  crate calls neither. Every play count on the phone is a permanent `0` — which
  is what the device run showed next to tracks that had just been played.

#### Decisions, grilled 2026-08-04

1. **Now Playing is an expanding bottom sheet from the mini player**, collapsed
   by predictive back. No navigation library and no back stack for a single
   second surface; the design's own metric list already carries a 28 dp bottom
   sheet.
2. **The wave gets built now**, as a custom track on Material 3 1.4's `Slider`
   rather than a slider from scratch. It is the one visual signature of this
   screen; without it Now Playing is every other player.
3. **`TrackRow` carries `id`**, mirroring the desktop, where a row is a full
   `Track` projection and the rating setter is called with `track.id` directly.
   No lookup per click, and `record_play` needs the same id.
4. **M3b records plays.** A number that can never change while the stars beside
   it can is the same half-truth as a sync screen with no backend.
5. **The 364 dp cover gets a measured rung, not the nearest desktop one.**
   364 dp at the target's 3× density is 1092 px; `ThumbnailSize::Full` is
   1024 px, a 6.6 % upscale on a screen-filling image. M3a refused exactly this
   ("do not force the desktop's ladder onto a density it was not measured for")
   and the same answer applies here.

#### The work

- [x] The sheet: 364 dp cover at radius 28, title 28/36, artist 16/24, growing
      out of the mini player and collapsing on back.
- [x] `ThumbnailSize::MobileFull = 1092`, resolved through the same lazy,
      off-main-thread path M3a built — one cover, not a list.
- [x] Seek, end to end: the session exports it, the wavy slider drives it.
      **While a drag is in flight the UI owns the position**; the snapshot tick
      resumes only after the release, or the head fights the player and stutters.
      Guard that with a test rather than by feel.
- [x] Shuffle and repeat: session setters plus two snapshot fields, so the
      buttons show the mode rather than merely setting it. **Prove `Repeat::One`
      actually replays against the core queue** — the fake backend never fires

- [x] `id` on `TrackRow`, and a rating that writes through. The setter is silent
      on a missing track, so the boundary — not the core — has to notice when a
      rating went nowhere and say so.
- [x] `record_play` behind `should_count_play`, which needs the session to track
      a per-track high-water position rather than the current one.
- [x] The action row only offers what exists.
- [x] Paging and the M3a artwork path stay untouched: the library list keeps
      stepping `200 → 400 of 1824`, covers keep resolving lazily per row.

### M5 — Themes

The owner: theme switching matters. It is also the one place where the mobile
surface should do something the desktop cannot.

#### Measured 2026-08-04 — and it corrects this plan

The line above said "the core knows nothing about themes". **That is wrong**, and
the correction changes the shape of the package:

- The **choice already lives in the core.** GTK persists it through
  `reprise_core::library::settings::{get_setting, set_setting}` under the key
  `"ui.theme"`, with the ids `perpetual-rain`, `night-terrain`, `muted-bloom`
  (`reprise-gnome/src/ui/style/theme.rs`). The core's settings table is a
  generic key/value store, so it already holds this without knowing what it
  means.
- The core additionally has a **typed** light/dark switch:
  `get_color_scheme` / `set_color_scheme` over `"ui.color_scheme"`, values
  `light`, `dark`, `system`.
- What is missing is neither storage nor a palette format: **the Android FFI
  exposes no settings at all**, in either direction. That is the actual work.
- The Android theme is one hard-coded `darkColorScheme(...)` in
  `ui/theme/NocturneTheme.kt`, applied unconditionally by `RepriseTheme`.
- `scripts/check-android-theme.sh` forbids a raw `Color(...)` anywhere except
  that one file, so a second palette needs the lint widened to the theme
  directory rather than a second exemption.
- Material You is reachable — `dynamicDarkColorScheme` ships in the material3
  the BOM already pulls in — but it needs **API 31+** while the module declares
  `minSdk = 26`, so it is a runtime branch, not a compile-time one.

#### Decisions

1. **The shared key is `ui.theme`, and neither surface rewrites what it cannot
   render.** A phone that reads `night-terrain` has no palette for it and falls
   back to its own default **without writing back** — otherwise a trip through
   the phone would silently destroy the desktop's choice. The same rule binds
   the desktop when it meets a mobile-only id.
2. **The three desktop palettes are not ported to Compose.** They are twelve
   GTK window/view/card colours; Material 3 wants some thirty semantic roles.
   Mapping one onto the other is *designing three new themes*, which is exactly
   what this plan refused for light mode. Mobile ships what it has.
3. **Dynamic colour is a theme id, not a modifier** — `ui.theme = "dynamic"`.
   It is "which palette", so it belongs in the same key, and rule 1 already
   says what every other surface does with an id it cannot honour.
4. **Nocturne stays dark-only; dynamic colour may follow the system.** The
   refusal to invent a light ramp stands — but a dynamic light palette is
   generated by the platform from the wallpaper, not invented by us, so when
   dynamic colour is chosen the existing `ui.color_scheme` decides light or
   dark. Nocturne ignores that switch, because it has nothing to switch to.
5. **The choice lives in the overflow menu for now, not in a settings screen.**
   M6 builds the 2a settings surface and will absorb it. Building half a
   settings screen here and moving it there is churn, and inventing its layout
   without the frame in front of us is the fabrication this project keeps
   refusing.

#### The work

- [x] **Settings cross the FFI** — a read and a write, typed at the boundary
      rather than a raw string pair if the shape allows it. This is the piece
      everything else in M5 and M6 stands on.
- [x] Android reads `ui.theme` at startup and applies what it knows: `nocturne`,
      `dynamic`, or anything else → Nocturne, **without writing the value back**.
- [x] **Dynamic colour on API 31+**, guarded at runtime, seeded from the
      wallpaper; on API < 31 the option is not offered at all rather than
      offered and ignored.
- [x] Nocturne remains the default and the fallback.
- [x] The theme lint widens to the theme directory, so a second palette lives
      beside the first instead of forcing an exemption.
- [x] A test that fails if a surface writes back an id it did not understand —
      the one rule that protects the other surface's choice.

### M6 — Playback settings, and what Android can actually honour

The owner: equalizer, crossfade and the rest belong in the Android settings
too. They do — but only the ones the platform can really deliver.

Measured in the core, already shared and persisted:
`AudioEffects { equalizer_enabled, equalizer_bands: [f64; 10], replay_gain:
Off|Track|Album }` plus `TrackTransition { Off, Gapless, Crossfade }` and
`crossfade_seconds: u8`.

| setting | Android | verdict |
| --- | --- | --- |
| **Equalizer** | `android.media.audiofx.Equalizer` on ExoPlayer's audio session | **Real.** Ship it — with the caveat below |
| **Gapless** | ExoPlayer does it natively for supported formats | **Real.** The setting maps straight through |
| **Crossfade** | ExoPlayer has **no** crossfade. Needs two players with volume ramps, or a custom audio processor | **Not a setting — a project.** Do not ship the slider before the effect |
| **ReplayGain** | Core stores only the *mode*, never per-track gains; ExoPlayer applies none | **Blocked.** Needs the scanner to store gains and a gain stage |

- [ ] **The 10-band array is a GStreamer shape, and it will not survive the
      crossing.** `android.media.audiofx.Equalizer` reports its own
      `getNumberOfBands()` — commonly five — at device-defined centre
      frequencies. Ten fixed bands is precisely the pattern this codebase has
      paid for five times already: *the caller knows something about the
      backend instead of asking it.* Start this package with a measurement
      task that produces no code and answers what the equalizer contract
      should be when one backend has ten fixed bands and the other decides for
      itself. Do not force the phone into ten bands, and do not silently
      resample the user's curve.
- [ ] Equalizer, gapless and the settings the core already carries, on the
      2a settings surface.
- [ ] **Crossfade and ReplayGain appear only when they work.** A slider that
      moves and changes nothing is the same lie as a sync screen with no
      backend. Record them as measured-and-deferred, with the reason.
