# M12 — the queue becomes visible, and a timer

Since M11 there are three ways to start music. There is still no way to change
your mind. Press play and the decision is final: you can skip forward, skip
back, or replace the whole thing. You cannot see what is coming, cannot drop the
one track you are not in the mood for, and cannot pull a song forward.

**The queue already exists.** `AndroidPlaybackSession` holds a
`reprise_core::queue::Queue` — the file's own first line calls it "Android's
Core-owned playback queue and transport surface". The boundary passes only
transport across it: pause, next, previous, seek, shuffle, repeat, snapshot. The
contents have never crossed.

So this package builds almost nothing below the boundary. Like M11, it is a
narrow Rust slice that exposes what Core already does, and a wide Kotlin slice
that draws it.

## What Core already does

- `remaining_window(offset, limit)` and `remaining_len()` — the future, paged,
  in exactly the window idiom every list in this app already uses.
- `move_item(from, to)`, `remove_order_positions(&[usize])`,
  `play_order_position_now(position)`, `jump_to_order_position(position)`.
- `queries::query_queue_item_window(db, items, offset, limit)` — resolves a
  window's ids to metadata with **one batched query**, never one per row
  (QUE-6), and does its own windowing.
- `library::session::{load, save}` with `QueueSnapshot` (ids, position, repeat,
  shuffled) and `Queue::restore_snapshot`, versioned, bounded by
  `QUEUE_LIMIT = 10_000`, and rejecting an invalid snapshot rather than
  panicking on it.

## What ships

**A queue page inside the Now Playing sheet**, reached by its own icon in the
sheet's header. The list replaces the artwork; the title row and the transport
stay where they are, so you hear what is playing while you rearrange what
follows — and can tell immediately whether the change was right.

Not a third entry beside *Cover* and *Ambient*. That switch answers "what is
drawn behind the track", a stored presentation choice. Putting navigation into
it would merge two unrelated things into one control.

**The list shows only the future** — `remaining_window`, paged in 200-row
windows like every other list. The playing track is not a row in it, because the
sheet already shows it directly above; a second copy would only raise the
question of which one is real.

**Tapping a row plays it now.** `play_order_position_now`, not
`jump_to_order_position`. Core's own comment says why: fast-forwarding the
playhead onto the target leaves everything it passed *behind* it, which drops
those tracks out of the forward list and "reads as *the whole list changed / my
upcoming songs vanished*". Against a future-only list that is exactly what would
happen — tap row five, watch four rows disappear. Promoting the track instead
lets one song jump the line while every other keeps its place.

**A visible drag handle reorders, a full-width swipe removes.** The handle
because reordering has to be findable — a long press hides the whole feature
behind a gesture nobody tries. The full width because a short flick while
scrolling would otherwise delete a row, and there is no undo: the swipe removes
from the queue only, never from the library, and rebuilding a queue costs one
tap on play.

**Nothing is enqueued from the library.** No *play next*, no *add to queue* on a
library row. That is what keeps the list flat: without manual entries there is no
manual section, and so none of the desktop's two-section model (QUE-2, *Next in
Queue* vs *Continuing from …*) is needed. `append_tracks` stays unused, and the
core's separate manual queue in `up_next.rs` stays unwired.

**The queue survives a restart.** Through `library::session::{load, save}` and
`QueueSnapshot`. Following the desktop (QUE-11), a cold start restores it
**paused** — it never begins playing by itself.

This is in the package rather than after it because making the queue visible
makes its disappearance visible too. Today nobody notices that the queue dies
with the process, because nobody could see it. After this package you would build
an order by hand, Android would reclaim the app in the background as it routinely
does, and the work would be gone.

**A sleep timer**, as a second icon in the same header. Fixed steps — 15, 30, 45,
60 minutes and *end of track*. While one runs, the control shows the remaining
time and a way to cancel it.

On expiry the volume fades over a few seconds and playback **pauses**. The fade
is the point: an abrupt cut wakes exactly the person the timer exists for. Pause
rather than stop, so the queue and position stay and the morning begins where the
night ended.

**The timer lives in the playback service, not in the composable.** A timer held
by the UI dies when the screen goes off — which is the one moment it is for. Its
remaining time is shown in the sheet; the notification is not extended.

## What is deliberately not guarded

**Toggling shuffle discards a hand-made order.** `move_item` rewrites only
`order`; `set_shuffle` replaces `order` wholesale in both directions
(`self.order = (0..self.ids.len()).collect()` on the way back to linear). So
reorder, shuffle on, shuffle off — and the arrangement is gone.

This is left alone. The desktop behaves the same way, and giving the phone a
second rule for the same queue would be worse than the loss. Pressing shuffle is
a visible statement that the current order does not matter. The case where it
stings — a careful arrangement, then the shuffle button pressed twice — is real
but narrow, and no cheap guard covers it: hiding the handles while shuffled does
not help, because that case starts with shuffle off.

Removal is not affected. `remove_order_positions` rebuilds `ids` as well, so a
removed track stays removed across any shuffle toggle.

## The hazard this package carries

**Rows are addressed by order position, and every removal shifts the ones after
it.** A position captured when a row was bound points at a different track by the
time the action fires — this is the podcast ✕ defect again, in a list that
renumbers itself far more often. Actions must carry the identity of the track
they belong to and resolve the position at the moment they run, never the other
way round. A test has to remove a row and then act on one below it.

The wide-short sheet layout (`WideShortNowPlayingContent`) needs its own answer
alongside the stacked one; the queue page must not be built for the tall layout
and merely tolerated in landscape.

## Proof

Every test mutation-proven: break the mechanism, show the real red output,
restore it, show green. A test that also passes without the change does not
count.

Cover at least: the list holds what follows the playing track, in play order,
and not the playing track itself; tapping a row promotes it and leaves the rest
of the list intact — with the count unchanged, which is what separates
`play_order_position_now` from `jump_to_order_position`; a drag reorders and the
next automatic advance follows the new order; a full swipe removes and a short
one does not; removing a row and then acting on a later row hits the track that
row shows; the queue and its position return after `ActivityScenario.recreate`
and after a cold start, paused; the timer fires from the service with the app
backgrounded, fades, and leaves the position where it was; cancelling a running
timer stops it.

Lifecycle claims run through `MainActivity.onCreate` and
`ActivityScenario.recreate`, never a directly wired composable — M7's warning,
M9a's answer. Say which path each test takes.
