# M7 — the playing track survives the activity

Follows M3a–M6 (merged as `aa1182f5fb`). One theme: **what is playing is a fact
the playback session owns**, and the surface should ask it rather than keep its
own copy.

## The defect

Rotating the phone recreates the activity. The mini player and the Now Playing
sheet go blank, because "what is playing" lives only in activity state:

```kotlin
internal data class PlaybackSelection(
    val tracks: List<LibraryTrack>,   // up to a whole window of rows
    val startIndex: Int,
)
```

`activeSelection` is retained so the list can tint the playing row and the mini
player can name the track. It does not survive `onDestroy`.

## The decision, and it is already made

**Nothing goes into `savedInstanceState`.** Writing up to 500 `LibraryTrack`
objects into a `Bundle` risks `TransactionTooLargeException`, and it would create
a *second* copy of something that already exists — the queue lives in Rust, in
`SessionState { track_ids: Vec<i64>, uris: Vec<String>, … }`, inside the playback
service, which outlives the activity by design. The activity rebinds to that
service after every rotation.

So the fix is not to save state. It is to **stop deriving the playing track from
a retained list** and read it from the session instead.

`AndroidPlaybackSnapshot` today carries `current_index` but nothing that names
the track. Both halves of the answer are already in `SessionState`; only the
accessor is missing.

## The work

### 1. The session says which track is playing

Add the current track's identity to `AndroidPlaybackSnapshot` — id and uri, both
derivable from `current_index` and the session's existing `track_ids` / `uris`,
`None` when nothing is loaded. This is the whole FFI change; do not add a way to
read the entire queue, because nothing needs it and an accessor with no caller is
a second thing to keep true.

Cover the empty queue, the index that is out of range, and the transition to a
new selection with tests in `reprise-android-ffi`.

### 2. The surface asks instead of remembering

`playbackPresentation` currently answers "is this the playing row" by indexing
into the retained selection. It should answer it from the snapshot's track
identity. Once it does:

- `PlaybackSelection` stops being retained state. It stays as the **argument** to
  `playTracks` — the list you chose to play — and nothing more.
- The mini player and the sheet render from the snapshot plus one track loaded by
  id, rather than from a list of up to 500.
- Rotation loses nothing, because there was nothing to lose.

Loading one track by id must go through the library the activity already holds.
If no by-id read exists, add one; do not reconstruct a track from the snapshot's
fields, because a half-track that renders is worse than an honest absence.

**A rotation with nothing playing must stay blank.** The bug is a blank surface
where something plays; the opposite mistake — a mini player showing a track after
playback ended — is worse, and the tests must forbid it.

### 3. The sheet's cover stops queueing behind the list

Separate commit, same theme. `ThumbnailSize::MobileFull` (1092 px) decodes on the
same single-thread executor as every 168 px row thumbnail, so opening the sheet
mid-scroll waits behind a queue of list covers the user is no longer looking at.

Give the full-size decode its own lane, or let it jump the queue. Decide which
after reading how the recycle token works today — whichever you choose, the
existing guarantee must hold: **a row that scrolled away may never overwrite the
cover of the row that replaced it.** Say in the commit which of the two you chose
and why the other was worse.

## Nothing on the owner's screen — absolute

Nothing may open a window, a dialog, a browser or an app in the foreground of the
owner's desktop, and nothing may take focus. No emulator, no `adb`, no launching
the app. If a step would put anything on screen, do not take it — report that it
needs the owner. Headless only: compilation, unit tests, gates.

Commit messages carry their reasoning; the repo squash-merges. Say plainly what
remains unverified without a device — the rotation itself is the obvious
candidate, since Robolectric recreates an activity without ever turning a phone.
