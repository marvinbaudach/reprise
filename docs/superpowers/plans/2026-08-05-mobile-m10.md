# M10 — the spectrogram reaches the phone

The desktop got a real spectral seek bar today (#289, #297). The phone still
draws a **sine wave it computed from nothing**: `WavySliderTrack` plots
`sin(x / 24dp · 2π)` under the playhead, which looks like a waveform and
measures no audio at all. M9c shipped a settings page whose *Spectrum* and
*Preview* rows are greyed out with "Needs track analysis", and that sentence is
true only until this package lands.

This package gives the phone the data and the three surfaces that show it.

## What already exists, so nothing is reinvented

- **`reprise-core::spectrogram`** — `TrackSpectrogram`, 24 logarithmic bands at
  20 frames per second, frame-major bytes, `SPECTROGRAM_FORMAT_VERSION = 1`.
  `SpectrogramAccumulator::push(&[f32])` / `finish()` knows no platform; it wants
  mono `f32` at `SPECTROGRAM_SAMPLE_RATE_HZ` (32 kHz).
- **`reprise-core::db_spectrogram`** — `set_track_render_data`,
  `get_track_spectrogram`, `set/get_waveform_peaks`, `track_source_fingerprint`,
  `pending_render_data_tracks`.
- **`reprise-view`** is toolkit-neutral and already holds what the picture *is*:
  `spectral_colour` (the coral→magenta→blue→teal OKLCH axis), `aggregate_rms`,
  `smooth_neighbors`, `shape_display_peaks` → `DisplayBar`. The GTK side only
  caches Cairo surfaces and paints them.
- **`RenderDataBackend`** is a trait whose default implementation answers
  honestly that the platform provides nothing. Linux fills it with GStreamer,
  producing peaks and spectrogram in one decode pass.

Android has **none** of it: no FFI, no Kotlin, no data.

## The seven decisions this plan rests on

Settled with the owner on 2026-08-05, after M9c landed.

**1. No picture without data.** Until a track is analysed the seek bar is flat —
the rule the brief already gives for a track without analysis. The invented sine
wave goes. It is the same defect class as M9b's FILL bug, one step worse: there
the surface drew a state it had and drew it wrong; here it draws a state it does
not have at all.

**2. Kotlin is a pump; the core does the arithmetic.** MediaCodec decodes (the
phone's hardware decoders, and no Rust decoder dependency), then hands raw PCM
*and its sample rate* across the boundary. **Resampling moves into the core**,
where the desktop never needs it because GStreamer already resamples. The band
plan, the FFT sizes, the 100 Hz bass split, the dB window and the byte encoding
stay in exactly one place. Two implementations of a **stored** format is two
different pictures of one song, discovered only when a sync puts them side by
side.

**3. Only what is playing, and only while it is visible.** No library-wide
sweep: at 480 bytes per second of audio a four-minute track is 115 KB and this
library is 1824 tracks — roughly 200 MB, plus 1824 decode passes, for pictures
nobody has asked to see. The seek bar and both visualisers only ever show the
playing track, and only the Now Playing sheet shows them (the dock has no seek
bar; the mini player has a plain progress strip). So the analysis runs when that
sheet is open and not otherwise.

**4. Closing the sheet cancels it.** Same signal as the screen going off in
M9b's performance rule; `extract_render_data_cancellable` is the shape the core
already has. **Nothing partial is ever stored** — a half spectrogram draws a bar
that stops mid-track, a picture claiming the song ends there. The next visit
starts over, which is cheap as long as decision 7's limit holds.

**5. All three surfaces.** Seek bar, *Spectrum* at the cover, *Preview band*.
Shipping the data without them would leave two settings rows saying "Needs track
analysis" about tracks that have one. Their look is **derived from the desktop**,
not invented: the preview band is the seek bar's rendering without playhead or
times, and Spectrum is the column of the current moment — 24 bands over the
cover — both coloured through `spectral_colour`. Colour and shaping come from
`reprise-view`, so phone and desktop cannot drift apart.

**6. Two measurements prove the two sides agree.** One in the core, one on a
device. See *Limits*.

**7. Limits are numbers in this plan, not "we will measure".**

## Limits

| what | limit | what it means if it breaks |
| --- | --- | --- |
| **Time** | A four-minute track: sheet opened → bar drawn in **≤ 5 s** on the emulator | The flat moment is too long; decision 1 reopens (a bar that grows, or analysing the next queue entries ahead of time) |
| **Memory** | Never more than **one second of PCM in flight** (~128 KB); no whole-track buffer, on either side of the boundary | The package is built wrong |
| **Main thread** | The analysis costs **no frame**. Measured, not asserted | The decode belongs further from the UI thread |
| **Accuracy** | Same file both ways: **99 % of cells within ±2 byte steps**, mean absolute difference **< 1 step**, mean *signed* difference ≈ 0 | Phone and desktop show two pictures of one song; the format question reopens |

The signed-difference term is not decoration: a systematic offset means one side
is uniformly louder, which the eye reads as a colour cast across the whole bar
while every per-cell difference stays inside tolerance.

## The two measurements

**In the core, an ordinary test.** The same PCM fed twice — once at 44.1 kHz
through the new resampler, once already at 32 kHz — must produce cells that meet
the accuracy limit. This needs no device and runs in every gate round. It tests
the resampler, which is the only new arithmetic in the chain.

**On a device, an acceptance run.** One track analysed on the desktop and the
same file analysed on the emulator; the stored bytes are pulled and compared
against the same limit. This tests what the core test cannot: MediaCodec against
GStreamer.

## The cut

Three runs with file ownership written into each prompt, because a file touched
outside the list is thrown away in the merge.

| run | content | depends on |
| --- | --- | --- |
| **A** | The core: the resampler and its test; the boundary — push PCM with its rate, store, hand back shaped bars | — |
| **B** | Android: the MediaCodec decode pass, bound to the sheet's lifetime, cancellable | A |
| **C** | The drawing: seek bar, Spectrum, Preview band; the settings rows enabling themselves per track | A |

**B and C run in parallel** once A is merged: B touches only the decode path, C
only the surface. C works against stored fixture data rather than waiting for B.

## Decisions taken here rather than asked

- The surface asks the core for **shaped bars at the width it has**
  (`shape_display_peaks(raw, count)`), rather than lifting 115 KB into Kotlin and
  shaping it there. Same reason as decision 2.
- The existing **source fingerprint** governs on the phone too: a re-tagged file
  is analysed again rather than showing the old picture.
- A track MediaCodec cannot decode keeps its **flat bar and its disabled
  entries**, with the reason that is then true. It is not retried in a loop.

## Proof

Mutation-proven as always: break the mechanism, show the real red output, restore
it, show green. A test that also passes without the change does not count.

Three that matter here:

- **The flat bar is drawn because there is no data, not because drawing failed.**
  Assert on what reaches the canvas, not on a flag the code computes itself —
  `MaterialSymbolFillTest` is the shape, and M9b is why.
- **Cancelling stores nothing.** Close the sheet mid-analysis and prove the row
  still has no stored spectrogram — and that the next visit produces a whole one.
- **One picture, two devices.** The accuracy limit above, both measurements.

Lifecycle claims run through `MainActivity.onCreate` and
`ActivityScenario.recreate`, never through a directly wired composable — M7's
warning, M9a's answer. Say which path each test takes.

## Nothing on the owner's screen — absolute

No window, no dialog, no browser, no app in the foreground. **No emulator, no
`adb`, no launching the app** — the device pass is mine, and this package leans
on it: the time limit, the frame limit and the cross-device accuracy limit are
all things a JVM test can only approximate.
