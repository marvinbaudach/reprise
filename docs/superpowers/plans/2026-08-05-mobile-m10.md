# M10 — an honest seek bar

**This package was planned as one thing and shipped as another.** The plan below
is kept in the shape it ended in, with the original intent and the reason it was
abandoned, because the reason is the useful part.

## What shipped

The phone's seek bar drew `sin(x / 24dp · 2π)` under the playhead — a wave
computed from nothing, which looked like a reading of the song and measured no
audio at all. It is now **one colour, filled to the playhead**, with the elapsed
time and the `−m:ss` remainder unchanged. The scrub gesture M9a proved is
untouched.

*Spectrum* and *Preview band* left the visualiser switcher; **Cover** and
**Ambient** remain. They had been shown greyed with "Needs track analysis",
which was true while the phone still computed one. It does not, so the line
explained a wait with no end. A stored choice of either falls back to the cover
**without writing** — the value belongs to whoever stored it, and a fallback
that overwrote it would decide for the other surface.

The stored format in the core is untouched: `TrackSpectrogram`,
`db_spectrogram`, the peaks. A sync package has somewhere to put what it carries.

## What it was going to be, and what that cost

The plan was for the phone to compute its own spectrogram — MediaCodec decoding
faster than playback, pushing PCM across the boundary into the core's
`SpectrogramAccumulator`, so that the seek bar, a spectrum at the cover and a
preview band could draw the desktop's picture from the desktop's own shaping and
colour axis in `reprise-view`.

It was built and it worked: on a Pixel 10 Pro XL a 2:36 track stored 75 024
bytes where the duration implied 75 019. Getting there cost two defects that
only devices could show, and both were the same wrong assumption — **that a
track's stored duration is exact**:

- **Too short, and everything was destroyed.** MP3 and Opus decode to slightly
  more samples than their tagged duration (encoder delay, padding, pre-skip,
  rounding), and the waveform accumulator treats one sample past its bound as a
  decode failure. The emulator's library is FLAC, whose durations are exact, so
  every test and every probe passed while a real phone — 62 MP3, 216 Opus —
  produced nothing at all, silently, forever.
- **Too long, and a lie was stored.** The emulator's fixture library carries
  real paths and metadata over roughly two-second audio files, and the app stored
  984 bytes as the finished analysis of a 172-second track. Nothing noticed.

And the third: the pass ran at `THREAD_PRIORITY_BACKGROUND`, which Android caps
at a few per cent of a core, so a 5:14 track took about as long as the song
while a listener watched the bar it was supposed to fill.

All three were fixed. The owner then judged the feature not worth what it costs
to keep correct, which is a judgement the measurements support rather than
contradict: it is a picture, and the desktop already computes it.

## Where it comes back

Whatever package carries the desktop's analyses to the phone. The boundary it
needs is not the one that was removed — that one took PCM and decoded; a sync
takes **stored bytes** and writes them. `set_track_render_data` is already the
shape for that, and the drawing is recoverable from this branch's history
(`5c1ef5de`, `0cc116db`) rather than needing to be invented again.

The standalone rule — *the phone must be whole without a desktop* — bends here
by an explicit decision rather than by neglect: without a sync no phone will ever
show a spectral bar, and that is accepted because the plain bar is not a
degraded one. It says exactly what it knows.

## Proof

Seven gates, each exit code on its own. **128 JVM tests in 26 classes**, zero
failures — the count M9c left, because everything this package added tested the
analysis that is now gone. `crates/reprise-gnome`: zero lines.

On the emulator: the switcher offers Cover and Ambient, "Needs track analysis"
appears nowhere, the seek bar draws one colour to the playhead, and the log
carries no fatal exception or ANR.
