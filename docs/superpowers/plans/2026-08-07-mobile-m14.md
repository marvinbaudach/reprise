# M14 — the analysis reaches a phone that already has the music

M13 shipped and was proven on hardware. The device pass found what the emulator
could not: **on a phone whose library is already synced, not a single analysis
arrives.**

The evidence is plain. A listener-started sync to a real Pixel 10 Pro XL, with
194 tracks already on the device, completed and wrote the ratings and play-count
list — 14 672 bytes, 194 entries, real play counts — and **zero** analysis
sidecars.

## Why

`copy_analysis_sidecar` is called from exactly one place: inside the `Ok(_)` arm
of a **track copy** (`device_sync_effects.rs:121`). There is no other call site,
and neither the planning nor the preparation code mentions sidecars at all. So a
sidecar only ever travels as a passenger of its audio. A track already on the
device is never copied, so its analysis never leaves the desktop.

This defeats the package's purpose. `run_render_data_backfill` can compute an
analysis for a whole library, and none of it will ever reach a phone that has
the music — the seek bar there stays plain for ever.

## The design flaw underneath

`is_managed_item_file` (`device_sync_inspection.rs:236-246`) is the **accept
predicate for the device inventory**, and M13 added the analysis sidecar and the
metadata list to its exclusions so the desktop would not see them as orphans to
delete.

That was right for deletion and wrong for everything else: it also made them
invisible to the planner. One predicate is answering two different questions —
*do I know about this file?* and *may I remove it?* — and they have different
answers for a sidecar.

The lyrics sidecar has the same shape and has never shown the problem, because
lyrics arrive with new music. An analysis is precisely the case where the audio
is unchanged and only the sidecar is new.

## What ships

**The inventory sees sidecars; the removal planner still leaves them alone.**
Split the predicate so that "known" and "removable" are separate questions.

**A missing sidecar is work.** When a track is on the device and its analysis
sidecar is not, the sync copies the sidecar — without recopying the audio.

**A sidecar of the wrong size is work too.** The inventory already carries
`size_bytes` for every managed file, and the desktop knows what its own encode
would produce, so this costs nothing. It is a coarse signal by design: it
catches an analysis that changed shape, not one recomputed to the same length.
Reading each sidecar back over MTP to compare fingerprints would cost a round
trip per track and is not worth it.

**The cargo rule is unchanged.** Analyses ride with every sync, automatic or
not; the ratings and play-count list still rides only with a sync the listener
started (`MTP-30`).

## Proof

Every test mutation-proven: break the mechanism, show the real red output,
restore it, show green. A test that also passes without the change does not
count.

The test that matters most is the one M13 did not have: **a device that already
holds every track, and no sidecars.** Today that plans no work at all; it must
plan one sidecar per track. Cover also: a device holding a sidecar of the right
size plans nothing for it; one holding a sidecar of the wrong size plans a
rewrite; a sidecar is still never removed as an orphan; and the audio is not
recopied merely because its sidecar is missing.

## Verification

The nine gates M13 established, including `reprise-gnome` and
`reprise-platform-linux`. The seven display-gated `device_sync` tests are the
session owner's, run individually.

Starting count: **2175 core**, **83 ffi**, **1572 gnome** (472 display-gated),
**136 platform-linux**, **153 JVM tests in 33 classes**.

## The pass that found this

Repeat it. A sync to a phone that already has the music is the case that broke,
and it is invisible on an emulator whose sidecars were placed by hand.
