# M13 — the desktop sends what it has already worked out

M10 planned for the phone to compute its own spectrogram, built it, and then
removed it: the feature cost more to keep correct than it was worth, and the
desktop already computes the same picture. What it left behind was deliberate —
the stored format (`TrackSpectrogram`, `db_spectrogram`, the peaks) was kept
untouched so that a sync would have somewhere to put what it carries.

This is that sync. It is also the first mobile package allowed to change the
desktop.

## One direction

Desktop → phone. Nothing travels back. That is enough for a start, and it
removes the entire question of conflict resolution: there is one source.

**The desktop wins, always.** The phone is a copy. Two consequences are
properties of this design rather than defects, and are written down here so
nobody later reports them as bugs:

- a heart set on the phone lasts until the next sync, and is then replaced by
  whatever the desktop holds;
- the play count can go **down**, because listening on the phone counts nowhere
  the desktop can see.

## What travels

- **The analysis** — the spectrogram and the waveform peaks the desktop has
  already computed. `run_render_data_backfill` can produce these for a whole
  library, so this is not limited to tracks that happen to have been played at
  the desk.
- **The play count.**
- **The rating.** A desktop **5** becomes a heart; **1 to 4** become no heart.
  That is not a new rule — the phone asks `list_favourites` for exactly five,
  and M11 pinned "a four is not a favourite" as a mutation.

## Derived data always, judgements only on request

`MTP-30` is **on by default**: connecting the phone starts a sync by itself,
with no button press. So the split matters.

- **Analyses ride with every sync**, including an automatic one. An analysis is
  arithmetic about a file; getting it wrong makes a bar look odd and nothing
  else.
- **Ratings and play counts ride only with a sync the listener started.**
  Otherwise the charging cable would be the button that resets the hearts set
  during the day, silently, with nothing asked and nothing said.

## How it travels

**The analysis rides as a sidecar next to its track**, exactly as synchronized
lyrics already do. `device_sync::lyrics_sidecar` is a pure path projection —
`paths_for_track`, `device_path_for_track`, `is_sidecar_path` — and
`crates/reprise-gnome/src/ui/device_sync/device_sync_effects.rs` is where an
attachment is actually sent alongside its audio. The analysis follows that
shape: matched by path, surviving a partial sync, and following the audio even
when the audio was transcoded to another extension.

**The ratings and counts ride as one small list** at the sync root. They are
about thirty bytes per track; a whole library fits in one file the phone reads
in a single pass. Per-track sidecars for them would mean thousands of file
opens for sixty kilobytes of information.

The two are not one mechanism because they are not one shape. An analysis is
roughly 480 bytes per second of music — about 115 KB for a four-minute track,
and hundreds of megabytes across a library. That belongs beside its track. A
rating does not.

## What the phone does with it

- **The list is read during the scan.** It is small, and it describes tracks the
  scan is walking anyway.
- **A sidecar is read when its track is first played**, and written into the
  database then, through `set_track_render_data` — the writer M10 identified for
  exactly this. Reading every sidecar at scan time would be hundreds of
  megabytes of work for pictures that may never be looked at.
- **A sidecar whose `track_source_fingerprint` does not match its audio is
  ignored**, not used. An analysis of a file that has since changed is worse
  than no analysis, because it looks authoritative.
- **A missing sidecar is not an error.** The plain seek bar stays exactly as
  M10 left it, and says precisely what it knows. Nothing about this package may
  make the phone worse when no desktop has ever touched it.

## Shape of the work

One package, two slices, because the only proof that counts here is the round
trip: the desktop writes, the phone reads, and the same picture appears. A
format written by one half and read by the other months later drifts; written
and read together, it cannot.

The desktop slice touches `crates/reprise-core/src/device_sync` (12 573 lines)
and `crates/reprise-gnome/src/ui/device_sync`. Both carry their own user-facing
rules — the `MTP-*` section of `docs/ux-rules.md` — and this package must obey
them rather than work around them. `MTP-30` in particular is not a detail here;
it is the reason the cargo is split in two.

## Proof

Every test mutation-proven: break the mechanism, show the real red output,
restore it, show green. A test that also passes without the change does not
count.

Cover at least: an analysis written for a track is readable for that track and
not for its neighbour; a sidecar whose fingerprint disagrees with its audio is
ignored and leaves the stored data alone; a missing sidecar leaves the phone
exactly as it was; a desktop five arrives as a heart and a desktop four does
not; a play count arrives; an **automatically started** sync carries analyses
and leaves ratings and counts untouched, while a listener-started one carries
all three; a partial sync leaves the tracks it did not reach alone.

Lifecycle claims on the phone run through `MainActivity.onCreate` and
`ActivityScenario.recreate`, never a directly wired composable.

## Verification

```
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test -p reprise-core --lib
cargo test -p reprise-android-ffi
bash scripts/check-android-theme.sh
bash scripts/android-build.sh
cd android && ./gradlew :app:testDebugUnitTest :app:assembleDebug
```

`JAVA_HOME=/usr/lib/jvm/java-21-openjdk`, `GRADLE_USER_HOME` inside the
worktree. Starting count: **2207 core**, **80 ffi**, **147 JVM tests in 30
classes**.

**Gradle reports `testDebugUnitTest` green without running it.** Delete
`android/app/build/test-results/testDebugUnitTest` first, compare every
`TEST-*.xml` mtime against the run's start, give the real numbers.

Unlike every mobile package before it, `crates/reprise-gnome` **may** change
here — but only under `ui/device_sync`, and the desktop's own test suites must
stay green. The GTK display tests are not part of this battery and are the
session owner's to run.

## Nothing on the owner's screen

No emulator, no `adb`, no launching the app, and no touching a real phone over
USB. The device pass is mine.
