# M8 — a counted play survives the process

Follows M7 (merged as `d898dde1f4`). One gap, named by `play_recorder.rs` itself:

> What this deliberately is **not** is a persistent queue: nothing here survives
> the process. A play still in hand when Android kills the service is lost,
> silently, because there is nobody left to tell.

Android kills media services routinely — swiped away, low memory, the system
deciding. Today that loses the play, and worse, loses it *quietly*.

## What already exists, and must not be broken

`crates/reprise-android-ffi/src/play_recorder.rs`: the session owns **one**
writer thread with one long-lived `Db` handle; the playback thread hands over
only a track id and the moment it happened. A play that loses to the scanner's
single folder-walk transaction is offered again `BUSY_ATTEMPTS = 4` times with
backoff, and giving up names the track. `RecordedPlay` is timestamped **where it
happened**, so a queued write cannot back-date `last_played_at` to the drain.

All of that stays. M8 adds durability underneath it, not a second mechanism
beside it.

## The decisions, already made

**1. The queue is a journal file, not a table.** Putting pending plays in SQLite
would put them behind the very lock they are waiting for — the scanner holds one
transaction for a whole SAF walk, which is exactly when a play cannot be written.
The journal lives in the app's private files directory, which the session
already receives.

**2. Exactly once, not at-least-once.** A play counted twice is silent data
corruption in something the user reads. Replay must not be able to double-count,
and "probably already applied" heuristics on `last_played_at` are not proof.

The mechanism: every journal entry carries a **monotonic sequence number**, and
the applied high-water mark is stored **in the same transaction** as the count
increment. Replay applies only entries above it. One integer, no growing
bookkeeping table, and exact — because the writer thread is single, so plays are
applied in order by construction.

`stats.rs` already carries `_in` variants that take a connection so a caller can
supply its own transaction (tag writeback uses one). Use that shape; if the
play-count increment has no `_in` form yet, give it one rather than opening a
second transaction.

**3. Write the journal *before* attempting the database, remove after commit.**
That order is what makes a kill survivable. It also means a kill *between* commit
and removal replays an entry that was already applied — which is precisely what
the sequence number makes harmless.

**4. The journal is bounded.** A permanently wedged database must not grow a file
forever. Decide the cap and what happens at it, and say why: dropping the oldest
and dropping the newest are different lies, and refusing to count further is a
third option. Whatever you choose, **it must say so** — the one thing this
module's own documentation calls out is that today's loss is silent.

**5. It stays in `reprise-android-ffi`, not `reprise-core`.** The desktop's
writer is not killed by an operating system mid-write. The only core-side change
should be the high-water mark's storage and, if needed, an `_in` variant. Do not
build a general durable-queue abstraction for one caller — see the crate's own
history with `MissingReason::Unknown`.

## What must be proven

- A play written to the journal and **not** applied is applied on the next open.
- A play applied and left in the journal (kill between commit and removal) is
  **not** counted twice.
- A journal that is corrupt or truncated mid-entry does not take the session down
  with it — a half-written last line is expected after a kill, not exceptional.
- Ordinary operation still does not stall the playback thread: the journal append
  happens on the writer thread, not where the event is emitted.
- The scanner-contention retry still behaves as before.

Each with a mutation proof: break the mechanism, show the real red output,
restore it, show green.

## Nothing on the owner's screen — absolute

Nothing may open a window, a dialog, a browser or an app in the foreground, and
nothing may take focus. **No emulator, no `adb`, no launching the app** — the
device pass is mine. Headless only: compilation, unit tests, gates.

Commit messages carry their reasoning; the repo squash-merges. Say plainly what
remains unverified without a device — a real process kill mid-play is the obvious
candidate, and a JVM test cannot stage one.
