# M9c — the settings screen, minus what it cannot do

Frame **12a**: seven views — Übersicht, Bibliothek & Scanordner, Audio (two
scroll states), Sync & Geräte (two), Darstellung.

The vocabulary is settled by the frame: small top app bar, **72 dp rows**,
section headings in **Primary** (`#4FDBD4`), M3 switches (52 × 32 dp track,
24 dp thumb; on = `#4FDBD4` track with `#003735` thumb). Primary text 16/22,
subtitle 13.5/19 in `neutral-400`, dividers 1 dp with 8/16 dp margins.

## Start here: the screen already exists

M6 shipped `PlaybackSettingsScreen.kt` — full screen, its own header, one
`LazyColumn` carrying Playback → Gapless, the Equalizer switch with the
device's live bands, and the theme choice. It opens from the library's overflow
menu. **This package restructures that screen; it does not write a new one.**
The equalizer block in particular is measured, device-near work from M6 and
moves unchanged.

## The rule this package is really about

Every row must do something. A settings screen is the easiest place in an app to
ship a lie, because a switch that flips looks like a switch that works.

Worse here than usual: **these settings live in the shared core.** A toggle on
the phone writes a value the *desktop* reads. A crossfade switch Android does not
implement would not merely be inert — you tap it on the phone, nothing happens on
the phone, and your desktop starts crossfading. That is a remote effect nobody
expects, and it is the reason the omissions below are omissions rather than
"greyed out for now".

## The seven decisions this plan rests on

Settled 2026-08-05 with the owner, after M9b landed. Each is here with its
reason, because the reason is what survives contact with the code.

**1. Übersicht with sub-pages, not one page with sections.** The frame's shape
wins, and the equalizer is why: seven vertical faders inside a collapsible
section inside a scrolling `LazyColumn` is the classic touch gesture conflict —
swipe-to-scroll against drag-the-fader. On the desktop with a mouse it does not
arise; on Android it does. A page of its own removes it; an accordion does not.

**2. The graph is local to the overlay.** `settingsVisible` stays the gate, and
a `NavHost` with the settings graph sits *inside* the overlay. Back on a
sub-page pops; back at the Übersicht closes the overlay, exactly as today.
The top level is state-driven and was proven on a device through M9a and M9b —
rotation, process death, dock, sheet — and nothing about a settings row is
improved by touching it. The price, stated so nobody rediscovers it: a later
deep link ("open settings → Audio" from a notification) has to go in two steps,
`showSettings(true)` then `navigate("audio")`.

`androidx.navigation:navigation-compose` is **not in the Compose BOM** and needs
its own pinned version.

**3. The desktop line ships with sync, not here.** The standalone decision of
this morning says the settings screen carries one line at the bottom whose tap
*is* the yes — the moment the network permission is asked and the search starts.
There is no transport, no pairing and nothing to find, so that tap would ask for
a permission and then honestly report "nothing found". A listener who sees that
once learns the feature is broken, not that it is missing. MTP is unaffected:
there the desktop does the work and the phone is a folder.

**4. Stars in library rows default to off, under a surface-scoped key.** Today
every row shows its rating. M9b's rule is that a library row shows stars only if
switched on. The switch writes **`ui.mobile.library_rating`** and nothing else:
the desktop's equivalent is not a boolean but a column
(`append_rating_column`, visibility through `ui.column_layout`), so one shared
boolean would either rip a column out of the desktop — the remote effect this
package exists to prevent — or be ignored there, which is a lie by omission.

Default off, because the row already carries title, artist, album, play count,
duration and the playing bars, and because the rating badge is the one thing on
it whose state was invisible for months without anyone noticing (see M9b's FILL
bug) — the best evidence available that nobody reads it there.

**5. The overflow menu keeps Rescan and Settings.** "Choose another folder"
moves into the library section entirely: it is configuration, not an action, and
there it finally stands next to the folder it changes and the count that folder
produced. Rescan stays in the menu **and** gains a second entry point beside the
count in the library section — the same ViewModel call from two plausible
moments: from the menu right after copying music over USB, and from the settings
screen when the count itself is what looks wrong. Two entries onto one method
cost nothing.

**6. One package, FFI first.** These are one screen; split, the first package
ships an Übersicht whose rows lead nowhere and the second rearranges what the
first just built. The device pass here is cheap — seven views, and the question
is whether any row lies. The only Rust is the new appearance key, so it goes
first and the Kotlin side never waits on regenerated bindings.

**7. Audio's subtitle carries no number.** "Gapless, Equalizer", not
"Equalizer · 5 bands". The band count exists only once there is an audio session
(`EqualizerBandsAbsence.NO_PLAYBACK_YET` is exactly that state), and the
Übersicht is seen when the app opens — guaranteed before the first playback. A
subtitle that filled the number in later would also have to take it back when
the session ends, so it would flicker twice per sitting instead of standing
still once. The band count belongs on the Audio page, beside the bands it
counts.

## What ships

**Übersicht.** The root list, one row per section that exists: icon, title,
subtitle, chevron. The subtitles are honest or absent:

| section | subtitle | where it comes from |
| --- | --- | --- |
| Bibliothek | `1824 titles · 1 folder` | the `total` of `list_tracks`, and the one SAF tree |
| Audio | `Gapless, Equalizer` | fixed, see decision 7 |
| Darstellung | the theme's name | `ui.theme` through `AndroidStoredTheme` |
| Über Reprise | the version | `BuildConfig` |

There is one scan folder, not several — `set_tree_uri` is singular, and the
frame's plural is desktop vocabulary. Album and artist counts are available the
same way (`list_albums` / `list_artists` return a `total`) if the row wants
them; a "last scanned at" does not exist anywhere and is not worth inventing
here.

**Bibliothek & Scanordner.** The folder the app holds, changing it, the counts,
and the second rescan entry point.

**Audio.** Gapless — real on both backends. The **equalizer**, moved unchanged,
and here the frame is a pattern rather than a specification: it draws seven
vertical faders at fixed frequencies (60 / 150 / 400 / 1k / 2.4k / 6k / 14k).
**Take the form, not the frequencies.** The band count and centre frequencies
come from the device's live audio session — five on the emulator, possibly ten
elsewhere — exactly as M6 built it. The fader layout (`Row`, `weight(1f)` per
band, 4 × 110 px track, 18 dp thumb, frequency label beneath) carries any count;
the labels come from the device. At ten bands on 412 dp the labels will crowd —
measure it and say what you did.

**Darstellung.** Theme (M5 already stores and shares `ui.theme`), Material You
where `DynamicTheme` already supports it, the **visualiser choice** — the same
stored value M9b writes from the long-press menu, with the same four entries and
the same disabled state for Spectrum and Preview, not a second value — and
**stars in library rows**, per decision 4.

The settings screen is where someone looks for a preference they cannot find by
long-pressing a surface they did not know was pressable. That is why the
visualiser appears twice; it is also why it must be one value.

**Über Reprise.** Versions and licence. Real strings, read from the build.

## What does not ship, and why

- **Sync & Geräte**, with its direction diagram, pairing, auto-sync toggles and
  history. There is no sync at all — no pairing, no transport, no queue of
  pending changes. The diagram is the best part of the frame and it explains an
  asymmetry that does not exist yet. The standalone decision's one line goes
  with it (decision 3).
- **"Als gespielt zählen ab."** The frame is right that it must match the desktop
  or the counts drift apart at every sync, and right that it should be taken from
  the desktop when pairing. There is no pairing, so a local default would be
  precisely the drift the warning warns about. The threshold stays where it is —
  `should_count_play` is half the track — until sync exists.
- **Crossfade.** The core carries the setting and the desktop implements it
  (`crates/reprise-platform-linux/src/crossfade.rs`, overlapping via a second
  GStreamer pipeline). ExoPlayer has no crossfade; it needs two players and a
  mixer. That is its own package, and until it exists the row would reach across
  and change the desktop.
- **ReplayGain.** Same shape, closer to reachable: `ReplayGainMode` exists in the
  core, but there is **no per-track gain column** — the values live in tags and
  nobody reads them on Android yet. Also its own package.
- **Bitgenaue Wiedergabe.** Genuinely buildable — `AudioTrack` at the file's
  sample rate, no resampling where the device supports it — but it is playback
  engineering, not a settings row, and it deserves its own package with its own
  device measurement.
- Skip silence, mono downmix, Bluetooth codec, output device, the four headphone
  behaviours. None have a backend. Note that **one of them half exists**: M7's
  `setHandleAudioBecomingNoisy(true)` already pauses on unplug — it is behaviour
  without a switch, which is the honest side of the same coin.

Every omission goes in `docs/mobile-2a-record.md` under the deliberate list, with
its reason. That file already separates decisions from unfinished work; this is
the largest batch it will have taken at once.

## Proof

Mutation-proven tests as always: break the mechanism, show the real red output,
restore it, show green. A test that also passes without the change does not
count.

Three that matter here:

- **A row that writes nothing must not exist.** Build the rows from one closed
  set of descriptors, each carrying its own reader *and* writer, and assert the
  rendered rows against that set. Maintaining the same list twice and comparing
  the copies proves nothing; deriving both from one place makes an unwired row
  fail the build instead of shipping.
- **The visualiser choice is one value.** Setting it in the settings screen and
  reading it where the long-press menu reads it must agree — this is the second
  writer of a value M9b introduced, and two writers of one setting is how M5's
  theme rule got written in the first place.
- **The back stack is a lifecycle claim.** M7's warning binds and M9a's answer
  is the shape to copy: a Robolectric test that wires a composable directly and
  never enters `MainActivity.onCreate` can stay green while a device fails.
  Anything asserted about popping, about the Übersicht's back closing the
  overlay, or about a sub-page surviving rotation runs through the activity and
  `ActivityScenario.recreate`. Say which path each test takes.
